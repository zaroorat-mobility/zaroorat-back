## 1. Executive Summary

A prior fix, already committed on this branch (`17fbfdc feat(ride): dispatch ride requests to nearby drivers automatically`), closed the single worst gap in this system: a ride request used to go to no driver at all. That is no longer true. A real ride request today can automatically reach an eligible online driver, and that driver can discover and accept it through a real, concurrency-safe path. This audit independently re-confirms that and finds it accurate.

What still stops the workflow from being a real, production-usable product, in order of how early it bites:

1. **Dispatch is one-shot.** If the single nearest driver offered a ride doesn't act on it, the request simply expires. There is no retry to a second candidate.
2. **Discovery ≠ delivery.** A driver can now _ask_ "do I have an offer?" (`GET /rides/offers`), but nothing pushes that offer to them. FCM tokens are collected and stored (`UserDevice.fcmToken`) but **never read by anything** — not the notification service, not the dispatch consumer, not any provider. There is no socket layer (`src/plugins/socket/socket.plugin.ts` is a literal `export {}`).
3. **The customer has no channel to learn their driver was assigned, and no way to see the driver's location, ever** — the one endpoint that holds live location (`GET /drivers/:id/location`) is authorization-scoped to the driver themself or `admin`/`support` staff, with no exception for a customer on an active ride with that driver.
4. **Fare is not admin-configurable.** A full pricing/surge/tax/cancellation-policy schema exists in Postgres and is never read by any service; fare is a static rate card resolved once from environment variables at process boot.
5. **A previously undiscovered, genuinely serious deployment-configuration risk:** the default role granted to every login is controlled by an unvalidated environment variable (`DEFAULT_USER_ROLE`), re-asserted on **every single login** (not just registration) via `AuthService.ensureDefaultRole`. If that variable is ever set to a seeded privileged role name (`admin`, `support`, `finance`), every user who logs in — new or existing — is silently granted that role, with no startup-time guard anywhere in the codebase to catch it. This is new to this audit; the prior report did not surface it.
6. **Wallet balances and settlement remain completely disconnected** from ride payment — confirmed again, and now with direct proof that `SettlementJob` is absent from _both_ the cron schedule (`JOB_SCHEDULES`) and the worker dispatch table (`MAINTENANCE_HANDLERS`) — it cannot run by any mechanism this codebase provides, not even manually via the job-name router.
7. **Vehicle-category validation at accept time is still absent**, and the `VehicleAssignment` table has no uniqueness protection of any kind (app or DB) — moot today only because no code ever writes to it at all.

What is genuinely solid, re-confirmed with fresh evidence this pass: OTP authentication (rate-limited, lockout, replay-safe), the ride state machine and its concurrency guards, trip-start OTP security, refund and webhook handling in the payments module (both are notably well-built — idempotency keys, signature verification, replay-window checks, amount-capping against stored state, not client input), and — new finding this pass — a real, substantial HTTP-level authorization test suite (`tests/integration/authorization-bola.test.ts`) that exercises exactly the BOLA/IDOR boundaries this audit was asked to check, for rides, drivers, and payments alike. It could not be executed in this environment (no reachable Postgres — see §29), but its content is strong evidence these boundaries were deliberately built and are meant to be continuously verified, not just claimed.

## 4. Auth Workflow

Re-traced `POST /api/v1/auth/otp/send` → `POST /api/v1/auth/otp/verify` → `AuthService.login` (`src/modules/auth/services/auth.service.ts`), with fresh attention to the specific questions this pass asks.

- **OTP send/verify route:** `src/modules/auth/http` registers them (mounted at `/api/v1/auth`); implementation in `OtpService.send`/`OtpService.verify` (`src/modules/auth/services/otp/otp.service.ts`), already deeply traced in the prior session and reconfirmed unchanged: Redis-backed challenge claim with resend cooldown, per-phone + per-device + per-IP rate limiting, single-use consumption, challenge-to-phone binding (prevents replay against a different number), attempt lockout, full audit-outcome trail. **VERIFIED.**
- **OTP replay:** cannot be replayed — `redisService.otp.consume` is single-use, and a second `verify` call for the same challenge fails the `assertChallengeBelongsToCaller` check once `verifiedAt` is set. **VERIFIED.**
- **Concurrent OTP requests (same phone):** the Redis `claimChallenge` call returns the existing active challenge rather than minting a second one — concurrent sends coalesce onto one challenge. **VERIFIED.**
- **User creation vs. lookup** (`auth.service.ts:355-403`, the private user-resolution method): looks up an active user by phone; if found, marks phone-verified/activates if needed; if not found, creates one; **and on every single path — existing, newly created, or the race-loser branch of a duplicate-phone insert — calls `ensureDefaultRole(userId, tx)`.** All three paths converge on the same role-assignment call. **VERIFIED.**
- **Default role assignment — VERIFIED, and a genuine new finding.** `ensureDefaultRole` (`auth.service.ts:409-414`) looks up `DEFAULT_ROLE_SLUG` (`src/modules/auth/constants/auth.constants.ts:3` — `process.env.DEFAULT_USER_ROLE ?? 'customer'`), and if the calling user doesn't already have an _active_ assignment for that role, grants it. **This runs on every login, not only first registration.**
  - **Is `DEFAULT_USER_ROLE` validated at startup?** Grepped `src/config/env/schema.ts` (the Zod-backed environment schema) for `DEFAULT_USER_ROLE`: **zero matches.** It is read directly via `process.env.DEFAULT_USER_ROLE` in a constants file, entirely outside the validated-environment layer. **NOT VALIDATED.**
  - **Can environment configuration accidentally grant a privileged role?** **Yes, and this is a real, exploitable-by-misconfiguration path, not a theoretical one.** If `DEFAULT_USER_ROLE=admin` (or `support`, or `finance`) is set and that role is seeded in the `roles` table (it is — `admin`/`support`/`finance` are referenced by name throughout the authorization layer, e.g. `payment.routes.ts:37`, `driver.routes.ts:19-25`), then **every user who logs in, forever, silently receives that role** — the only guard is `if (!role) throw` when the _slug itself_ doesn't exist in the seed data, which does nothing to stop a syntactically valid but dangerous slug. This is **P0** — see §30.
  - **Does login silently re-grant a revoked default role?** **Yes, specifically for the default role.** `ensureDefaultRole` checks `findActiveAssignment`, not "was this ever revoked" — if a user's `customer` (or whatever the default is) assignment is revoked (`revoked_at` set), the very next login re-grants it, because the check only asks "do they have an active one right now." This is **intentional-looking self-healing behavior for the baseline role** (reasonable for `customer`) but the mechanism itself does not distinguish "was never granted" from "was explicitly revoked" — if an operator ever revokes a user's default role as a moderation action, it silently comes back on next login. Non-default roles (`driver`, `admin`, etc.) are untouched by this path and stay revoked correctly.
- **Session creation, access/refresh tokens:** `TokenService`/`RefreshTokenService`/`SessionService`, re-confirmed present and structurally sound from the prior deep pass — refresh rotation via `tokenService.rotate`, idempotency-key-guarded (`refresh(refreshToken, idempotencyKey)` uses `redisService.idempotency.runOnce`), session-cap enforcement (`sessionService.enforceCap`) with a **higher cap for privileged roles** (`capForRoles`, `auth.service.ts:421-426` — checks `admin`/`support` membership). **VERIFIED.**
- **Device registration / FCM token:** `POST /auth/*` login accepts an optional `fcmToken` in the request body (`auth.schemas.ts:15`), which is persisted onto the `UserDevice` row (`device.repository.ts:11,54`) and echoed back in the auth response shape (`auth.responses.ts:62`). **Collected: yes. Stored: yes.** **Read anywhere outside the auth module: no** — grepped the entire notifications module and the new ride-dispatch consumer for `fcmToken`: zero matches. **Sent to an actual push provider: no such provider exists** (§21). **STUB / COLLECTED-BUT-UNCONSUMED.**
- **Logout / logout-all:** `AuthService.logout(sessionId)` calls `sessionService.logout`, re-confirmed present; "logout all" behavior (revoking every session for a user) was not re-traced line-by-line this pass — **NOT VERIFIABLE** to the same depth as the rest of this section, flagged rather than assumed.
- **Role revocation vs. existing JWTs / epoch invalidation:** `epoch-invalidation.consumer.ts` remains the mechanism that would force existing tokens to stop being honored on a security-relevant change; re-confirmed it is registered as a real event consumer in `bootstrapEvents()` (`src/bootstrap/events.bootstrap.ts`), same as before. The **exhaustive list of what triggers an epoch bump** (does role revocation itself trigger it?) was not re-traced to certainty this pass — **NOT VERIFIABLE**, carried forward as an open question from the prior audit rather than newly resolved.

**Quote snapshot — the brief's critical question, answered precisely:** `RideRequestService.createRequest` computes a fare quote and **does** persist a snapshot of it onto the `RideRequest` row at creation time (`quotedFare`, `estimatedDistanceKm`, `estimatedDurationMin`, `surgeMultiplier` — all written via `RideRequestRepository.create`). **This is a real, working quote snapshot at the request level.** However:

## 30. P0/P1/P2/P3 Findings

**P0 — Production/security/data integrity blockers**

1. **Unvalidated `DEFAULT_USER_ROLE` can silently grant a privileged role to every user on every login.**
   - Affected step: #7.
   - Files/symbols: `src/modules/auth/constants/auth.constants.ts:3` (`DEFAULT_ROLE_SLUG`), `src/modules/auth/services/auth.service.ts:409-414` (`ensureDefaultRole`), `src/config/env/schema.ts` (no validation entry for `DEFAULT_USER_ROLE`).
   - Proof: `ensureDefaultRole` is called unconditionally on every login path (existing user, new user, race-loser) and grants whatever role `DEFAULT_ROLE_SLUG` names if the caller doesn't already hold it. The env var is read via bare `process.env.DEFAULT_USER_ROLE`, entirely outside the Zod-validated environment layer — confirmed by a zero-match grep.
   - Realistic failure scenario: a deployment or CI configuration error sets `DEFAULT_USER_ROLE=admin` (or copies a `.env` from an internal/staging tool that had it set for testing convenience); every subsequent login — customer or otherwise — silently receives the `admin` role, since `admin` is a seeded, real role referenced throughout the authorization layer.
   - Recommended owner/module: Auth. Dependency order: independent of everything else in this report — fixable in isolation (a startup-time allow-list check against a small constant set of non-privileged default-role slugs) without touching any other module.

2. **A driver's trip-start OTP has no confirmed delivery path to the customer.**
   - Affected step: #29.
   - Files/symbols: `LifecycleService.acceptRideRequest` (`plaintextOtp` returned in the driver's own accept response), no customer-facing endpoint or event found that surfaces it.
   - Proof: exhaustive trace of every response shape and event payload touching `RideOtp`/`plaintextOtp` in `src/modules/rides` found exactly one consumer of the plaintext — the driver's accept-response body.
   - Realistic failure scenario: the product's stated security model (customer reads the OTP aloud, driver types it) cannot function today, because the customer's client has no way to obtain the code at all — only the driver's client does, which is backwards from the intended flow and, if the driver's app naively displayed it, would defeat the entire purpose of the OTP (proving the _customer_ is physically present) rather than reinforcing it.
   - Recommended owner/module: Rides (data) + Notifications (delivery) jointly. Dependency order: should be fixed before or alongside item 3 below, since both are "the customer needs a way to receive something."

3. **Settlement is completely unreachable in production — not scheduled, not handler-registered, no caller anywhere.**
   - Affected step: #39, cascading to #40.
   - Files/symbols: `src/jobs/scheduler/index.ts` (`JOB_SCHEDULES`, no settlement entry), `src/jobs/workers/index.ts:24-34` (`MAINTENANCE_HANDLERS`, no settlement entry), `SettlementService.calculateSettlement` (zero production callers).
   - Proof: direct re-read of both dispatch tables this pass; both enumerate the same nine job names, neither includes settlement.
   - Realistic failure scenario: drivers accrue `DRIVER_PAYABLE` ledger balances indefinitely with no mechanism, automatic or manual (via the job-name router), that ever converts that into a payable settlement or a wallet credit — this is a direct, ongoing financial-integrity gap for any driver actually completing paid rides in this system today.
   - Recommended owner/module: Payments. Dependency order: can be fixed independently (add the two missing table entries + decide/implement the wallet-crediting step) once the team decides whether wallet balance should be ledger-derived or settlement-derived — a design decision this audit does not make on the team's behalf.

**P1 — High-risk production defects**

4. Dispatch is single-shot with no retry to a next candidate on timeout/reject (§11, #19/#22). Files: `dispatch-timeout.job.ts`, `ride-requested.consumer.ts` (`MAX_CANDIDATES_TO_TRY = 1`).
5. No delivery channel for any ride event beyond polling — FCM tokens collected and never consumed (§15, §21, #22/#26/#33). Files: `src/plugins/socket/socket.plugin.ts` (stub), no push provider exists.
6. Customer cannot view driver location under any authorization path (§15, #27). File: `driver-identity.ts` (`authorizedDriverId`), no ride-scoped exception.
7. `vehicleId` on ride accept is not validated for driver ownership or category match; `VehicleAssignment` has no uniqueness protection at either layer (§12, §26, #25). Files: `ride.schemas.ts` (`acceptRideRequestSchema`), `vehicle.prisma:64-81`.
8. Wallet balances never move from ledger activity, independent of the settlement gap above — even a manual settlement run today would produce a `DriverSettlement` row, not a wallet credit, per `calculateSettlement`'s own implementation (§19, #40).
9. "One active ride per driver" and "one active ride per customer" are both application-only with a real (if narrow) TOCTOU race — no DB backstop for either, unlike the "one ride per request" invariant which does have one (§10, §13, §26, #18/#24).
10. No `RideRequest`-level cancellation endpoint exists — a customer cannot cancel a not-yet-matched request except by waiting out the 5-minute expiry (§10, new finding this pass).

**P2 — Important before scale**

11. Admin fare/pricing configuration does not exist as a feature — everything is static env config (§8, §9, #14/#15).
12. Cancellation fee is recorded as charged but never actually charged through any ledger/payment path (§22).
13. Final fare relies entirely on driver-submitted actuals with no GPS cross-check (§18, #35).
14. No real routing/geocoding/service-area enforcement (§7, #11-13).
15. Waiting-charge component is wired into fare calculation but `waitTimeMin` is never actually measured/written anywhere (§18).
16. Rating and support/dispute modules are schema-only, no service layer (§23, #41).

**P3 — Improvements**

17. No idempotency key on `POST /rides/requests` (§10).
18. Driver eligibility (required documents) is checked at go-online time, not re-verified per dispatch offer (§11).
19. `GET /rides/:id`-family response shape for driver/vehicle fields is deliberately minimal (`driver: { select: { userId: true } }`) — reasonable for authorization, but leaves nothing to build the customer-facing "driver info" feature on top of without further work (§14).
20. No profile-completion gate before reaching Home — may be intentional product behavior, flagged for confirmation rather than assumed to be a defect (§5).

## 31. Recommended Dependency-Aware Implementation Order

Built strictly from what's verified to already exist, reusing every real primitive this audit found rather than proposing anything speculative. Each stage is scoped to leave the repository buildable and independently testable.

**Stage 1 — Close the two cheap, isolated P0/P1 gaps that need no new abstractions**

- Goal: remove the privileged-default-role risk; add the missing driver-active-ride and vehicle-ownership checks that already have the data they need.
- Modules: Auth (role validation); Rides (vehicle check at accept).
- Existing code reused: `ensureDefaultRole`, `acceptRideRequestSchema`, `LifecycleService.acceptRideRequest`.
- New code required: a small allow-list/deny-list check on `DEFAULT_ROLE_SLUG` at startup (Auth config validation layer); a vehicle-ownership + category lookup inside `acceptRideRequest` (requires the `vehicles` module to gain at minimum a read model — this is the one place in this stage that touches a currently-empty module, kept minimal by design).
- Files likely affected: `src/config/env/schema.ts` or a new startup assertion; `src/modules/rides/services/lifecycle/lifecycle.service.ts`; a minimal new read path in `src/modules/vehicles` or a repository added to `drivers`.
- Dependencies: none — independent of every other stage.
- Acceptance: a startup check rejects a privileged `DEFAULT_USER_ROLE`; an accept call with a vehicle that doesn't belong to the driver or doesn't match the category is rejected with a clear error.

**Stage 2 — Get the trip-start OTP to the customer**

- Goal: close the P0 "OTP has no confirmed path to the customer" gap.
- Modules: Rides (data already exists), Notifications (needs to actually be called).
- Existing code reused: `RideOtpService.generateStartOtp`, `NotificationService.sendSms` (the one real send function that exists).
- New code required: a call from `acceptRideRequest` (or a customer-facing endpoint) that delivers the plaintext OTP to the customer via the one channel that already works — SMS — as an interim measure ahead of any richer in-app delivery.
- Files likely affected: `lifecycle.service.ts`, possibly a new customer-facing OTP-read endpoint if SMS delivery alone isn't judged sufficient.
- Dependencies: none beyond Stage 1 being merged first for cleanliness (not a hard technical dependency).
- Acceptance: a customer receives the trip-start code through some real channel, verified by an integration test asserting an SMS-send call fired with the correct code for the correct ride.

**Stage 3 — Multi-candidate dispatch with retry**

- Goal: close the "one attempt only" gap in matching.
- Modules: Rides (the consumer already exists and does the hard part).
- Existing code reused: `RideRequestedConsumer`, `NearbyDriverService.find` (already returns an ordered candidate list, not just the nearest one), `DispatchTimeoutJob` (already runs on a schedule).
- New code required: extend `DispatchTimeoutJob` (or a new small job/consumer) to, on a timed-out offer, re-invoke the same eligibility-and-offer logic against the next candidate in the original search result (or a fresh search) rather than just marking it `TIMEOUT` and stopping.
- Files likely affected: `dispatch-timeout.job.ts`, possibly extracting the candidate-selection logic out of `ride-requested.consumer.ts` into a shared function both it and the timeout job call.
- Dependencies: none on Stages 1-2.
- Acceptance: a request whose first-offered driver never responds automatically reaches a second eligible driver before expiring.

**Stage 4 — Settlement and wallet wiring**

- Goal: close the P0 settlement-is-dead gap.
- Modules: Payments only — explicitly do not mix this into Drivers (per the brief's rule).
- Existing code reused: `SettlementService.calculateSettlement`, `SettlementJob`, `LedgerRepository`.
- New code required: register `SettlementJob` in both `JOB_SCHEDULES` and `MAINTENANCE_HANDLERS` with a sensible cadence and a driver-enumeration step it currently lacks (something must produce the `driverIds` list it requires); a wallet-crediting step at the point settlement (or, alternatively, each ledger post) is confirmed — this is a design decision (ledger-derived balance vs. settlement-derived balance) this audit flags but does not make.
- Files likely affected: `src/jobs/scheduler/index.ts`, `src/jobs/workers/index.ts`, `SettlementService`, `WalletService` (connecting it to whichever trigger is chosen).
- Dependencies: none technically, but should be reviewed alongside the design decision above before implementation starts.
- Acceptance: a completed, paid ride is reflected in the relevant driver's wallet balance within one settlement cycle, verified end-to-end against a real (test) database.

**Stage 5 — Real-time delivery (notifications first, then live tracking)**

- Goal: turn "discovery" into "delivery" for offers, and give the customer any visibility into their assigned driver.
- Modules: Notifications (push provider), Rides (event wiring), Drivers (a ride-scoped location-read exception).
- Existing code reused: `RIDE_EVENT_CATALOG` (already publishes every relevant event, just to nobody), `UserDevice.fcmToken` (already collected, just unread), `NearbyDriverService`'s live position store.
- New code required: a push provider (FCM SDK integration) and consumers for `ride.dispatch.offered` (→ push to the offered driver) and `ride.accepted`/`ride.driver_arrived`/`ride.started`/`ride.completed` (→ push to the customer); a ride-scoped authorization exception on `GET /drivers/:id/location` for the customer of that driver's currently-assigned active ride.
- Files likely affected: a new `src/modules/notifications/providers/fcm.provider.ts`, new consumers alongside `ride-requested.consumer.ts`, `driver-identity.ts`'s `authorizedDriverId`.
- Dependencies: benefits from Stage 3 (multi-candidate dispatch) being in place first, so a push notification is going to the right driver on the right attempt, but not strictly blocked by it.
- Acceptance: a driver receives a push notification when offered a ride (not just a pollable row); a customer with an active ride can read their assigned driver's current location and no one else's.

**Stage 6 — Admin-managed pricing**

- Goal: close the largest single missing feature (§8, §9).
- Modules: a real `pricing` module (currently a stub) + Admin (currently a stub, needs to exist for CRUD routes) + Rides (`FareService` needs to read from it instead of env config).
- Existing code reused: the entire `pricing_rules`/`surge_zones`/`tax_configs`/`cancellation_policies` schema (already modeled, never read); `FareService`'s calculation shape (the arithmetic itself is correct, only its data source needs to change).
- New code required: admin CRUD routes and services for pricing rules; a versioned/effective-dated read path `FareService` calls instead of `rideConfig.rateCardsByVehicleType`; the quote-to-completion snapshot consistency fix flagged in §9 (completion should read the rate-card version that was active at quote/request time, not re-resolve fresh).
- Files likely affected: new `src/modules/pricing/*` and `src/modules/admin/*` (no longer stubs), `src/modules/rides/services/fare/fare.service.ts`, `RideRequest`/`Ride` (may need a stored rate-card-version reference if one doesn't already fit into the existing `quotedFare` snapshot).
- Dependencies: none of the above stages block this one, but it is the largest, so sequencing it last among P0/P1-motivated work is deliberate — it is a P2 finding, not a P0/P1 one, despite being the single biggest chunk of net-new work.
- Acceptance: an admin can change a fare component through an API and see it reflected in the next quote, without a deploy; a ride's final fare demonstrably uses the rate-card version active when it was quoted, even if pricing changes mid-ride.

## 32. Final Production Readiness Decision

**CONDITIONAL GO — for a controlled pilot only, not a public launch, and only once the three P0 items in §30 are closed.**

This is a genuine improvement over where this system stood at the start of this session: the one gap that made the entire workflow structurally impossible — no driver ever learning a request existed — is fixed, verified again from scratch this pass rather than taken on faith, and the concurrency guarantees protecting the money-and-assignment-critical moments (one winning driver, one ride per request, atomic OTP verification, balanced double-entry ledger posting, idempotent refunds) are all independently confirmed sound, several of them proven by real HTTP-level tests this audit did not previously give full credit for.

It is not ready for real users today because of three specific, independently fixable things, not a systemic redesign: an unvalidated environment variable that can silently hand out admin access to everyone (§30 #1), a trip-start security code with no confirmed way to reach the person it's meant to protect (§30 #2), and a driver-earnings pipeline that stops dead the moment money would need to actually reach a wallet (§30 #3). None of these require rebuilding anything that already exists — §31 lays out exactly what to reuse and what's genuinely new for each.

Everything below P0 (retry-on-timeout dispatch, real-time delivery, admin pricing, vehicle validation, rating/support) is real product-completeness work, correctly judged P1/P2 rather than launch-blocking, and can proceed in parallel with or after the P0 fixes without re-deriving anything this audit already established.
