# DRIVER ONBOARDING IMPLEMENTATION VERIFICATION

## 1. Executive Summary

This report verifies the current implementation of the Driver Onboarding flow following recent fixes. The core identity components (Auth, OTP, User, Files) are robust and shared securely with the Customer App. The Driver module now correctly enforces an explicit entry into onboarding, preventing the previous implicit `GET /me` side effect. Email collection is successfully integrated. However, the completion of the profile phase currently lacks explicit state management on the backend, relying entirely on the frontend to gate access to the Documents phase.

## 2. Current Driver Module Structure

The module is encapsulated within `src/modules/drivers/` and uses standard dependency injection.

- **Routes:** `driver.routes.ts` defines explicit endpoints for `/me`, `/me/onboard`, `/:driverId/profile`, and documents.
- **Controllers:** `DriverOnboardingController` orchestrates the HTTP layer.
- **Services:** `OnboardingService` manages creation, updates, and document handoffs.
- **Repositories:** `DriverRepository` and `DriverDocumentRepository` interact with Prisma.

## 3. Existing Onboarding Implementation

The onboarding implementation correctly delegates identity to the shared JWT mechanism. It establishes a `Driver` and `DriverProfile` record distinct from the `User` record, mapping exactly one driver per user.

## 4. Auth/OTP Integration

**PASS:** The Driver module does not reimplement Auth. It natively relies on `callerId(req)` which extracts the authenticated user from the JWT generated by the existing OTP flow.

## 5. User Integration

**PASS:** Email updates during Driver profile creation correctly reach back into the `User` model (`client.user.update`), ensuring synchronization between Customer and Driver profiles.

## 6. Driver Creation

- **Endpoint:** `POST /api/v1/drivers/me/onboard`
- **Controller:** `DriverOnboardingController.onboard` -> `OnboardingService.onboardDriver`.
- **Identity:** Forced via `callerId(req)`. The client cannot pass arbitrary `userId` or `driverId`.
- **Concurrency:** `OnboardingService` gracefully handles Prisma `P2002` duplicate errors, returning the already-created driver if simultaneous requests arrive.

## 7. Driver Profile

The profile is stored across two models:

- **Name (`fullLegalName`), Gender (`gender`):** `DriverProfile` table.
- **Email (`email`):** `User` table.
  The `updateDriverProfileSchema` accepts all fields and the `DriverRepository.updateProfile` gracefully orchestrates the split database writes.

## 8. Email

**PASS:** Email is validated via `z.string().email().max(100)`, captured, and persisted directly to the `User` table within the same onboarding request.

## 9. Validation

**PASS:** Zod handles all validations at the route boundary (`updateDriverProfileSchema`).

- Name: `min(2).max(100)`
- Gender: strict enum `['MALE', 'FEMALE', 'OTHER']`
- Email: standard email format, `max(100)`

## 10. Authorization

**PASS:** Endpoints implicitly rely on `callerId(req)` and the explicit `actingDriverId` function which ensures a user can only access their own driver record.

## 11. BOLA (Broken Object Level Authorization)

**PASS:** The `actingDriverId(req, this.driverRepository)` abstraction maps the secure JWT `userId` directly to a `driverId` and validates possession. The controller entirely ignores `req.params.driverId` for mutation actions, preventing IDOR.

## 12. Customer vs Driver

**PASS:** Calling Customer endpoints does not create a Driver. Creating a Driver requires explicitly calling `POST /me/onboard`. Furthermore, completing onboarding does NOT automatically assign the backend `DRIVER` role; the driver remains `PENDING` verification status.

## 13. Onboarding State

**MISSING / FAIL:** There is no explicit "Onboarding State" field in the database tracking "PROFILE_COMPLETE". The `verificationStatus` tracks document verification (`PENDING`, `DOCUMENT_REVIEW`), but the transition from entering profile details to moving to the documents screen is handled implicitly.

## 14. Profile Completion

**MISSING / FAIL:** Because there is no explicit state, there is no single backend function that validates "Name + Gender + Email are complete" to lock the profile phase. A client could technically start submitting documents before the profile is fully filled.

## 15. Resume

**PASS:** Data is persisted immediately via `upsert` in `DriverRepository.updateProfile`. If a driver force-quits the app, logging back in and hitting `GET /me` restores all entered fields.

## 16. Idempotency

**PASS:**

- `POST /me/onboard` twice: safely returns existing driver via `P2002` catch.
- `PATCH /profile` twice: `upsert` handles overwrites seamlessly without duplicates.

## 17. Concurrency

**PASS:** Explicit Prisma `P2002` (Unique Constraint) error catching in `OnboardingService.onboardDriver` makes concurrent creation safe.

## 18. Database

**PASS:** `Driver.userId` and `DriverProfile.driverId` both enforce `@unique` constraints.

## 19. Events

**PASS:** `DRIVER_EVENT_CATALOG.ONBOARDED` is published transactionally alongside creation.

## 20. API Response

**PASS:** `DriverOnboardingController` safely returns `{ data: profile }`. Sensitive data isn't leaked across boundaries.

## 21. Error Handling

**PASS:**

- Missing driver on `GET /me`: returns `DriverNotFoundError` (404).
- Invalid fields: Zod schema returns standard validation errors.
- Unauthenticated: Trapped by `callerId()`.

## 22. Tests

**MISSING:** There are no dedicated HTTP integration tests in `tests/integration/` for the `POST /me/onboard` or `PATCH /:driverId/profile` flows.

## 23. Documents Handoff

**PARTIAL:** The backend accepts document uploads (which implicitly shifts `verificationStatus` to `DOCUMENT_REVIEW`), but it does not tell the frontend `nextStep = DOCUMENTS`. The frontend must infer this boundary.

## 26. P0

**None.** Critical security, concurrency, and implicit creation bugs have been resolved.

## 27. P1

**Profile Completion State:** The backend does not enforce a strict "Profile Complete" boundary before allowing document uploads.

## 28. P2

**Missing Integration Tests:** The driver onboarding HTTP flows are completely untested in the `tests/integration/` suite.

## 29. Recommended Decision

**PROCEED WITH CAUTION.** The onboarding flow is functionally safe and secure from a data integrity perspective (no IDOR, no concurrency bugs, email is captured). However, without explicit profile completion states on the backend, the frontend owns the responsibility of ensuring all fields are filled before proceeding to documents. Tests must be written before final launch.
