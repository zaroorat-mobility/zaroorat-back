# Prisma Infrastructure

This directory houses the entire database abstraction layer for Zaroorat, organized to scale with a monolithic repository.

## Directory Structure

- **`schema.prisma`**: The generated/compiled monolithic schema that Prisma understands. Do not edit this directly.
- **`modules/`**: The true source code for our schemas. We split domains into isolated `.prisma` files here (e.g. `user.prisma`, `ride.prisma`). Run `npm run prisma:merge` to compile these into the root `schema.prisma`.
- **`migrations/`**: Generated by Prisma Migrate. These are the incremental SQL scripts applied to the database.
- **`seed/`**: Environment-aware seed data. `index.ts` automatically routes to `development.ts`, `testing.ts`, or `production.ts` based on `APP_ENV`. Run `npx prisma db seed` to execute.
- **`sql/`**: Unmanaged raw SQL scripts. Use these as templates for creating migrations that Prisma doesn't support natively (e.g., PostGIS Geography columns, Partial Unique Indexes, Range Partitions).

## Development Workflow

Every developer should follow this sequence when making database changes:

1. Edit `.prisma` files inside `prisma/modules/*`
2. `npm run prisma:merge` (combines modules into schema.prisma)
3. `npm run prisma:format` (formats the schema)
4. `npm run prisma:validate` (validates the schema)
5. `npx prisma migrate dev --name <migration_name>` (generates and applies the migration locally)
6. `npm run prisma:generate` (generates the Prisma Client into `src/generated/prisma`)
7. Run tests

## Production Workflow (CI/CD)

For production deployments (e.g. GitHub Actions), the sequence is different. **Never use `migrate dev` in production.**

1. `npm run prisma:merge`
2. `npm run prisma:validate`
3. `npm run prisma:generate`
4. Build Docker image
5. Deploy
6. `npx prisma migrate deploy` (applies pending migrations safely)
