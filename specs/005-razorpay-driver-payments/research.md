## R-3 Checkout inside the Expo driver app

**Facts about the app** (code): Expo SDK `~57.0.26`, React Native `0.86.3`, `newArchEnabled=true`, `android/` is **gitignored** (Continuous Native Generation — native changes must come from config plugins, precedent `plugins/withMappls.js`), EAS profiles `development`/`preview`/`production` exist (`eas.json`), scheme `zarooratdriver`, `expo-web-browser` and `expo-secure-store` already installed, no payment SDK installed.

**Facts about the SDK** (docs): official package `react-native-razorpay`. The latest version is **3.0.0** (npm, checked 2026-10-19). Its `package.json` declares `codegenConfig` `{ name: "RNRazorpayCheckoutSpec", type: "modules" }`, which is a TurboModule spec, and peer `react-native >= 0.66.0`. Its README still says nothing about the New Architecture, documents no cancellation error codes, and its example reads only `razorpay_payment_id` from the success data. Other facts: Expo users run `npx expo install react-native-razorpay` then prebuild; "doesn't work with the tools like expo which doesn't support native modules" (i.e. not in Expo Go); proguard rules `-keep class com.razorpay.** {*;}` etc.; iOS UPI intent needs `LSApplicationQueriesSchemes` `["tez","phonepe","paytmmp"]` set via app config ([README 2.3.1](https://cdn.jsdelivr.net/npm/react-native-razorpay@2.3.1/README.md), [RN Android steps](https://razorpay.com/docs/payments/payment-gateway/react-native-integration/standard/integration-steps-android), fetched). Android: targetSdk ≥ 30 needs a `<queries>` block listing UPI app packages for the UPI Intent flow ([Android payment methods](https://razorpay.com/docs/payments/payment-gateway/android-integration/standard/payment-methods.md), search).

**Unknown**: whether `react-native-razorpay` works bridgeless on RN 0.86. The 3.0.0 `codegenConfig` points to yes, but nothing documents it. RN 0.82+ runs bridgeless only, and a legacy bridge module without interop support would fail at runtime. Also unknown: whether `razorpay_order_id` and `razorpay_signature` reach JS in the success data on this version (Razorpay's RN integration page says they do). The spike records both, plus the error codes for dismissal, failure and network loss.

**Decision (TD-1)**: Use `react-native-razorpay` (Standard Checkout, native UPI intent) **behind a mandatory build spike** (task T005): an EAS development build on a real Android device must open checkout in test mode and return success, failure and dismissal correctly. Native configuration comes from a new config plugin `plugins/withRazorpay.js` (Android `<queries>` for `upi` scheme and UPI app packages, proguard keep rules; iOS `LSApplicationQueriesSchemes`).

**Fallback (TD-1b)**, chosen only if the spike fails: Razorpay Standard Checkout **web** page served by the backend (`GET /api/v1/payments/checkout/:intentId`, short-lived signed token) opened with `expo-web-browser` (Chrome Custom Tabs on Android, which hands `upi://` intents to UPI apps), Razorpay `callback_url` → backend verifies → redirect to `zarooratdriver://payments/return?intentId=…`. Same backend contracts, same verify and status endpoints; only the app-side launcher differs.

**Rationale**: matches Rapido's public choice (Standard Checkout) and Razorpay's own React Native guidance; the fallback keeps the delivery unblocked without a native dependency.

**Alternatives considered**:

- Razorpay checkout inside `react-native-webview` — rejected: WebView UPI handling needs custom `upi://`/`intent://` interception (community reports of UPI missing in WebViews); Custom Tabs avoid that.
- Razorpay Payment Links — rejected as primary: extra hosted page and redirect hops; acceptable as an emergency manual channel for support only.
- Custom UI / S2S UPI APIs / Turbo UPI — rejected: more PCI and compliance surface, more code, no benefit at our volume.
- Expo Go compatibility — impossible for any native payment SDK; the team already uses EAS builds.

## R-4 Webhook freshness vs. the constitution

**Facts**: Razorpay retries failed deliveries "in exponential backoff policy for 24 hours after event creation timestamp"; non-2xx is failure; 5-second response window; duplicates expected; dedupe on `x-razorpay-event-id`; ordering not guaranteed ([best practices](https://razorpay.com/docs/webhooks/best-practices/), [validate & test](https://razorpay.com/docs/webhooks/validate-test/), fetched). The Razorpay signature covers the **body only** — there is no signed delivery timestamp — and the body's `created_at` is identical on every retry. Code rejects events older than `PAYMENT_WEBHOOK_TOLERANCE_SEC` (300 s default, 3600 s max) **before** deduplication (`webhook.service.ts:82,147-157`; pinned by `tests/integration/payment-webhook.test.ts:129-138`). Stripe, by contrast, re-signs every retry with a new `t=` timestamp and says not to use `created` to decide processing ([Stripe webhooks](https://docs.stripe.com/webhooks), fetched).

**Decision (D-1, approved)**: Razorpay events are deduplicated first, processed up to **72 h** old, and beyond that stored + acknowledged + alerted + not applied (reconciliation fetches the truth). Stripe uses only the signed header tolerance. Constitution §9.4 ("timestamp tolerance … is not weakened") is **amended** to make tolerance provider-specific — amendment AM-1 in [decisions.md](./decisions.md).

**Rationale**: for Razorpay a freshness window cannot distinguish a retry from a replay (nothing time-related is signed); replay safety actually comes from (1) signature authenticity, (2) durable dedupe, (3) idempotent state transitions. A 300-second window adds no financial protection and drops legitimate retries.

**Alternatives considered**: remove the age check entirely (rejected: keep a bound for alerting on anomalous traffic); keep 300 s (rejected: loses payments after any 5-minute outage); body-derived secondary dedupe key (deferred: intent-level idempotency already makes header-swapped replays harmless; YAGNI).

## R-5 Payment identity and reconciliation

**Decision (TD-2)**: One "provider truth" function in the Razorpay adapter — `GET /v1/orders/{orderId}/payments` — that returns only a payment whose `order_id` equals our order, `status` is `captured`, `amount` equals the expected paise and `currency` is `INR`; it returns the `pay_…` id. Used by reconciliation, the `confirm` route and the new `verify` route. The webhook path applies the same validation gate to the payload's `payment.entity` (Razorpay payloads carry `amount`, `currency`, `order_id`, `status` — [payment payloads](https://razorpay.com/docs/webhooks/payloads/payments/), [order payloads](https://razorpay.com/docs/webhooks/payloads/orders/), fetched).

**Rationale**: closes F-01/G-03 (cross-order credit, lost `pay_` id, unrefundable payments) and G-14 (no amount check) with one shared check rather than per-path logic.

**Alternatives considered**: separate `payment_attempts` table now (deferred to the checkout-attempt analytics need; the partial unique index on succeeded `payment_transactions.gateway_txn_id` gives the durable guarantee with a smaller change); fetching every webhook's payment from the API (rejected: payload already signed and complete; extra latency against the 5-second window).

## R-6 Order receipt and idempotency

**Decision (TD-3)**: Razorpay `receipt` = `"zr1_" + first 32 hex chars of SHA-256(scopedIdempotencyKey)` (36 ASCII chars, deterministic, unique per request). Order creation: try `POST /v1/orders`; if Razorpay answers that the receipt was already used, recover the order with `GET /v1/orders?receipt=…` and continue. Recharge keys are scoped server-side as `recharge:{driverId}:{clientKey}` (subscription keys are already scoped); a replayed key belonging to another user is rejected; the Redis "in flight" marker gets a 120-second TTL separate from the 24-hour result TTL (TD-6).

**Rationale**: satisfies Razorpay's 40-character limit (N-01) and constitution §8.3 ("the external call carries a deterministic idempotency key so a recovery attempt returns the original effect"). Hash, not the raw key, so the receipt never exceeds 40 characters whatever the client sends.

**Alternatives considered**: receipt = application-generated intent UUID (rejected: not deterministic across a crash-retry, so the retry creates a second order — harmless but against §8.3); truncating the key (rejected: collisions).

## R-7 Recovery: outbox, jobs, dead letters

**Facts** (code): outbox delivery is at-least-once, 8 attempts with full-jitter backoff capped at 30 s, then `FAILED` with no requeue path (`OutboxRelay.ts:7-9,60-86,183-186`); `SubscriptionReconciliationJob` is registered in DI only and never scheduled (`subscriptions/index.ts:25`, absent from `jobs/queues/index.ts:28-39`, `jobs/scheduler/index.ts`, `jobs/workers/index.ts:41-61`); the intent reconciliation job scans 100 unordered PENDING/PROCESSING rows and never FAILED ones (`payment-intent-reconciliation.job.ts:14,51-58`).

**Decision**: schedule subscription reconciliation every 5 min, selecting pending subscriptions joined to SUCCEEDED intents, oldest first; intent reconciliation rotates by a new `last_reconciled_at` column and includes FAILED intents for 5 days (D-3); dead-lettered payment/subscription events alert and can be re-run by an operator through an audited admin action (D-5); a pending subscription keeps one order across failed attempts (TD-11), and a captured payment that matches no open subscription opens a refund review case (D-6).

**Alternatives considered**: raising outbox attempts (rejected: delays detection, does not fix permanent errors); auto-replaying dead letters on a timer (rejected: hides bugs; human-triggered but cheap is safer for money events).

### Constraints (not defects, but they shape the design)

- A newly seeded feature flag is created **ON**. A flag that does not exist reads as OFF (`feature-flag.service.ts:13-37`). TD-12 needs `defaultStatus`.
- `isEnabled` upserts every seeded flag on every call (K-7).
- The app auto-generates a fresh `Idempotency-Key` for each payment POST unless one is passed (`client.ts:209-211`). TD-8 passes the attempt key explicitly.
- `isDefinitiveRejection` treats every 4xx except 408, 409, 425 and 429 as a final refusal, and a final refusal restores the reservation (`refund.service.ts:345-366,521-528`). Once the idempotency header exists, Razorpay's 400 for a changed body under the same key must count as unknown (CD-14, T085). Find-before-create runs first and protects the normal case (fourth review).
- Razorpay refund webhooks are not handled. `payment.refund.processed` / `payment.refund.failed` in `events/catalog.ts:11-13` are internal outbox events (MI-11).
- Every payment route shares `rl:payment`: 20 requests per hour per user (`rate-limit.config.ts:27-32`, K-18).
- Alert rules are not kept in this repository. Metrics are served at `/metrics` (`worker-health.bootstrap.ts:27`), and the ops docs require every page-level alert to link to a runbook (`docs/14_Operations/01_incident-response.md:32`). Hence T099 and U15.
- The historical `CUSTOMER_WALLET_TOPUP` branch still credits a customer wallet on a late capture (`intent.service.ts:267-303`); see UD-11.

### Missing implementation (planned, nothing exists)

`verify` and status routes; checkout payload; provider sweep; review cases and suspense; job-run records and job-stopped alerts; dead-letter requeue; dual webhook secret; kill switch and pilot allowlist; app checkout, attempt store and status screens; Expo config plugin; admin payment lookup, review queue, dead letters, reconciliation runs and the real wallet tab; payment runbooks; alert rules; Razorpay refund-webhook handling. Refund unknown-outcome handling is **not** missing (E-6).
