## 4. VK-1: which idempotency key `verify` uses

**C8** (decisions.md §2c, approved): "Retries of the same logical attempt reuse the same idempotency key. No new attempt until the existing intent's authoritative state is resolved."

**The contract text** (contracts/http-api.md) says the app's interceptor adds the key, which means a fresh key per request.

**What the backend does today** (the code is unchanged by this packet):

- Verify is scoped by user, route and key (`intent.controller.ts`, `idempotency.repository.ts`).
- The same key with a different callback → `409 DUPLICATE_IDEMPOTENCY_KEY`.
- The same key with the same callback replays the first answer for 86 400 s by default (`PAYMENT_IDEMPOTENCY_TTL`).
- While a request is still running → `409 IDEMPOTENCY_IN_PROGRESS`, for up to 120 s.
- Each call counts against `rl:payment`, 20 per hour per user.
- **Duplicate credit is prevented on the server whatever the key.** The test "credits exactly once for a verified capture, however often verify is repeated" passed 12/12 in both 2026-10-22 runs.

|                                    | V1: reuse the recharge attempt key                                    | **V2: one key per callback**, `attemptKey:razorpayPaymentId` | V3: fresh key per request              |
| ---------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------- |
| Meets C8?                          | Yes                                                                   | **Yes**: retries of the same callback reuse its key          | **No**                                 |
| Same callback retried              | Replays the first answer                                              | Replays the first answer                                     | Runs again, with a new Razorpay lookup |
| A second payment on the same order | **409 every time**; it settles only via the webhook or reconciliation | Gets its own key; processed                                  | Processed                              |
| Duplicate wallet credit            | Prevented on the server                                               | Prevented on the server                                      | Prevented on the server                |
| Stale replayed answer              | Possible: the app reads freshness from `GET`                          | Possible: the app reads freshness from `GET`                 | None                                   |
| Backend change needed              | None; contract text updated                                           | None; contract text updated                                  | None                                   |

**Recommendation (not an approval): V2.** It meets C8 and keeps a later payment on the same order verifiable. It needs no backend change, only an update to the contract text. The app already treats `GET /payments/intents/:intentId` as the only source of truth, so a stale replay cannot mislead it.
